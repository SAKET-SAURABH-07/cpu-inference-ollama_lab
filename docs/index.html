Predict first, then measure.

Analysis

This section reads the measurements above. It is separate from the repo's own post-mortem, which has not been written yet; the predictions file says discrepancies belong there.

  • Decode beat both the range and the estimate

    The pooled mean of 45.42 tok/s is 4.6% above the 43.42 tok/s the predictions file computes from 21.34 GB/s and the 491,400,032-byte model file. Twelve of the 15 samples are above that estimate. The three below it are all in run 1.

  • Reading every model byte once per token does not fit the numbers

    At 45.42 tok/s, that assumption would need 22.05 GB/s using the model size llama-bench reports (485,452,288 bytes), or 22.32 GB/s using the file size. Both are above the 21.34 GB/s theoretical peak of one DDR4-2667 channel, and the model is far larger than a desktop CPU's cache.

    So either each token touches fewer bytes than the file holds, or the 21.34 GB/s figure is not the right ceiling for this machine. The predictions file names the first as its biggest risk. Which bytes are skipped is still open; the GGUF inspector step listed in the repo would show whether the model has a separate output matrix.

  • Prefill varies more than decode

    Prefill per-process CV ranges from 1.65% to 5.03%, and run 1 is above 5%. The variation prediction covered decode only, so this is not a miss. Prefill samples also move around inside a run; the last three repetitions of run 1 rise from 336.7 to 380.0.

  • The three processes disagree by more than their own spread

    Decode means are 44.02, 45.87 and 46.39 tok/s, a gap of 5.4% from lowest to highest, while the standard deviation inside a process is 0.84 to 1.50. Run 1 opens at 45.5 and 45.8, then drops to about 43 for three samples. Runs 2 and 3 stay between 44.5 and 46.9. Three processes show the variation but cannot say what caused it.

Limits of this baseline

  • One machine, one model, one quantization, one thread count.
  • Power plan was Balanced and boost clocks were not recorded, which the predictions file lists as a confound.
  • The environment snapshot taken with the benchmark was recorded with uncommitted changes in the repo. A later snapshot, taken on a clean tree, reports the same llama.cpp build and power plan.

Not in the repo yet

  • docs/postmortem.md, where the decode discrepancy is meant to be explained.
  • The thread-scaling sweep at 1, 2, 4, 6 and 12 threads.
  • The Q8_0 model run, needed for the Q4_K_M ÷ Q8_0 ratio.
  • The GGUF tensor inventory that settles the embedding question.

The command 

# one process; repeated three times, 5 repetitions per test
llama-bench -m qwen2.5-0.5b-instruct-q4_k_m.gguf \
  -p 512 -n 128 -t 6 -ngl 0 -r 5 -o json

-p 512 measures prefill on a 512-token prompt (pp512). -n 128 measures decode of 128 tokens (tg128). -ngl 0 keeps every layer on the CPU. -t 6 uses one thread per physical core.

Rules the repo sets for itself

  • Predictions are frozen.

    Corrections go in a separate post-mortem file, so the original guesses stay readable.

  • Raw output is never overwritten.

    The runner opens result files in exclusive-create mode and fails if one exists. stdout, stderr and a session metadata file are all kept.

  • Statistics are recomputed.

    The analysis reads per-repetition samples and warns if its mean or standard deviation disagrees with the tool's own.

  • Pooling is checked.

    Rows are only combined if build, model, threads, batch sizes, cache types, layers, load mode, repack and flash-attention settings match.

  • Assumptions are labelled.

    The bandwidth line in the analysis output is marked as assumption-dependent and not a measurement of memory traffic.

  • Tests use hand-checkable numbers.

    Five unit tests on synthetic samples such as 1, 2, 3, explicitly not benchmark results.

Structure

The repo is named for Ollama, but the benchmarks call llama-bench from llama.cpp directly. The model and llama.cpp binaries are git-ignored and live outside the repo.

Setup

CPUIntel Core i5-12400F, 6 cores and 12 threads. Benchmarks used 6 threads. Backend library: ggml-cpu-alderlake.
MemoryOne 16 GB Kingston DDR4 module at 2667 MT/s in slot DIMMB1. One module means one channel, so peak bandwidth is 2667 × 10⁶ × 8 bytes ≈ 21.34 GB/s. 15.86 GB visible to the OS.
OS and powerWindows 11 (10.0.26300), Balanced power plan.
llama.cppBuild 11871, version 0.7.0-dev, commit b3fa69955, built with Clang 20.1.8.
ModelQwen2.5-0.5B-Instruct, Q4_K_M, 491,400,032-byte file. llama-bench reports 485,452,288 bytes and 630,167,424 parameters.
Runtime settingsBatch 2048, micro-batch 512, f16 key and value cache, weight repacking on, flash attention on auto, no GPU layers.
ToolingPython 3.12.4 in a virtual environment, psutil 7.2.2.
